Index Subscriptions — the catalog watch, as a subscription

StallRow's Verdict Index snapshots the full x402 Bazaar catalog about every 6 hours and diffs it snapshot-to-snapshot. An index subscription turns that diff into a feed for your stall: register a filter once, and every delivered evaluation pushes the full diff for your listings — adds, removals, price changes, payTo rotations — to your webhook. Empty diffs arrive as heartbeats, so silence never masquerades as health.

How it works

StepCallPrice
RegisterPOST /v1/index/subscribe with a filter (pay_to, origin, or service), a webhook URL, and a Fleet Pass id for fundingfree
BaselineFirst evaluation stores your starting snapshotfree — never debited
EvaluatePOST /v1/index/subscription/run — diffs the newest snapshot against your watermark and pushes it to your webhook $0.10 debited from your Fleet Pass per delivered evaluation (the /v1/index/changes price)
StatusPOST /v1/index/subscription/statusfree

Funding honesty is built in: if your pass can't cover an evaluation, the run reports funding_failed and your watermark does not advance — you never lose a diff to a dry pass, and a failed delivery on our side refunds the debit. Freshness is enforced in code (since 2026-10-27): if the newest snapshot has aged past the freshness window, evaluations are skipped, not faked — no debit, no watermark advance — until a fresh snapshot lands.

Live dogfood: our own stalls, on our own subscription

Verdict Row eats its own cooking. On 2026-10-27 we registered our own fleet on the subscription — filter pay_to = the fleet payTo, funded by our own $5 Fleet Pass:

POST /v1/index/subscribe
→ {"reg_id": "isub_0bae95e3ed874ed4", "status": "active",
    "funding_kind": "fleet_pass", "created_at": "2026-10-27T17:05:44Z"}

POST /v1/index/subscription/run        (first evaluation)
→ {"status": "baseline", "snapshot_id": 3,
    "current_at": "2026-10-27T11:39:12Z", "debited_units": 0}

When snapshot #4 landed, the ticker-driven evaluation delivered: the subscription's watermark advanced to snapshot 4, its status reads delivered, and $0.10 was debited from the Fleet Pass — exactly the priced amount, visible in the pass's own debit ledger. A manual run after that answers honestly that there is nothing new to deliver yet:

POST /v1/index/subscription/run        (after the #4 delivery)
→ {"status": "no_new_snapshot", "snapshot_id": 4}

Correction (2026-10-27): an earlier version of this page described a second evaluation that "refused" because a snapshot-ingest run had failed a settlement-signature reconciliation check. That event never occurred — no such ingest component or check exists in the service, and the evaluation in question delivered, as shown above. Writing the page exposed a real gap, though: the subscription had no freshness guard, so it would have delivered against a stale snapshot if the snapshot ticker ever failed. That guard has since been shipped (and the paid diff route refuses stale pairs the same way), so the skipped evaluation the earlier page imagined is now the service's actual, tested behaviour:

POST /v1/index/subscription/run        (when the newest snapshot is stale)
→ {"status": "skipped",
    "reason": "latest index snapshot is stale (captured …,
               beyond the freshness window); refusing to diff against
               stale data",
    "debited_units": 0}

What a delivered evaluation looks like

A delivered run returns (and webhooks) the complete diff for your filter since your last delivered evaluation: listings added and removed, and field changes with before/after values — the same diff the fleet's public drift board renders for the whole catalog, narrowed to your stall.
